# Praxis 产品章程

> 本文是 Praxis 的顶层产品约束，优先级高于任何单次实现便利。修改本文件本身即是一次产品决策，需要走完整设计流程。

## 定位

Praxis（知行合一）是一个**个人数字花园**：记录知识、实践、成长、项目与思考的长期实践系统。

- 它不是普通博客，不是 CMS，不是模板站。
- 首页是表达理念的 Landing Page（Hero / Philosophy / Now / Practice Heatmap / Latest / Footer），不是文章索引。
- 三个理念阶段——知而思（know-think）、思而行（think-act）、行而成（act-achieve）——是方法，不是导航栏目。

## 决策优先级

任何设计与实现冲突时，按此顺序裁决：

1. 产品设计
2. 用户体验
3. 长期维护
4. 代码质量
5. 开发效率

绝不为了开发方便降低产品质量。发现当前架构存在长期问题时允许重新设计，不因沉没成本坚持错误方案。

## 事实源与架构红线

- **Markdown/MDX + Git 是唯一事实源。** 未来允许 FastAPI + PostgreSQL 作为增强层，但数据库永远不能替代 Markdown；没有后端、没有数据库时网站必须能完整构建。
- 统一 Content Collection：`type` 组织内容，`stage` 表达实践进度，`journey` 沉淀长期成长，`practiceLog` 记录真实实践事件。字段保持可扩展，不为当前需求写死 schema。
- URL 永久稳定：`/blog/`、`/notes/`、`/journal/`、`/projects/`；`stage` 不进入 URL。
- Practice Heatmap 数据来自站点自身内容，不是 GitHub Contributions，永不接外部活动 API。
- 只记录已经发生的实践，不用虚构内容填充页面。

## 视觉与体验

- 高端编辑型设计：Content First、大量留白、优秀中文排版、统一网格与设计系统、原创。
- 避免炫技动画、复杂渐变、为视觉牺牲可读性。
- 所有颜色/字体/字号/间距/阴影/圆角统一 Design Token（`tokens.css`），Light/Dark 双主题都经过设计。
- 全站在无 JavaScript 时完整可读；只有显式交互（如主题切换）渐进增强。

## 工作模式

每个新功能必须依次经过：需求分析 → 产品设计 → UI 草图（文字）→ 技术架构 → 文件结构 → 确认方案 → 编码 → Review。禁止直接跳到编码。

方案输出包含：产品设计、技术设计、UI 设计、数据结构、文件结构、API（如未来需要）、风险、以及为什么这样设计。多方案必须分析、比较、给出推荐和理由。

## 已裁决的章程偏差

- **React**：技术栈允许"少量交互组件用 React"，但当前实现为零框架且这是刻意的（无 JS 可读、CSP `script-src 'self'`）。裁决：React 是未来授权而非现在义务——出现原生脚本难以维护的复杂交互（如全文搜索）时再引入，并作为完整功能走设计流程。
- **roadmap 内容类型**：章程内容模型包含 roadmap，当前注册表（`domain.ts`）未含。裁决：内容先行——第一篇真实 roadmap 内容出现时再扩展注册表，避免空路由违背"只展示已发生的实践"。
